# Phase 1: Make CornerIQ Easier to Understand

Status: implemented locally; automated and human verification required
Updated: 2026-07-18

## Product Outcome

Phase 1 makes initial setup easier to follow, lets boxers record all training they already do, and makes ownership clear between existing training and work prescribed by CornerIQ.

## Onboarding Flow

The onboarding wizard uses six grouped screens. Each screen keeps related information together.

1. **Basic information**
   - Preferred name
   - Age
   - Sex used by the engine: Female, Male, or Prefer not to say
   - Current body weight
   - Typical walk-around body weight
   - Height
   - Preferred units
2. **Boxing background**
   - Amateur or professional status
   - Current level
   - Years of boxing experience
   - Stance
3. **Available training days**
   - Days CornerIQ may use
   - Supported equipment only: Bodyweight, Jump rope, Dumbbells, Barbell, Pull-up bar, Heavy bag, or Full gym
4. **Existing training schedule**
   - Recurring training entered by the boxer
   - Any combination of Boxing, Sparring, Strength, and Conditioning
   - Weekday, total duration, and expected effort
   - No start-time field
5. **Cycle support**
   - Optional private cycle-aware support
6. **Training goal**
   - Build phase
   - Fight camp
   - Fight camp branches to Single fight or Tournament after shared setup is complete

The previous health questionnaire and wearable-preference steps are removed. The five-page post-onboarding tutorial is replaced by one setup-complete screen.

## Training Goals

Athletes choose between two plain-language goals:

| Choice | Meaning |
| --- | --- |
| Build phase | Overall improvement without a scheduled competition. |
| Fight camp | Preparation for a single fight or tournament. |

Fight Camp asks whether the athlete is preparing for a single fight or a tournament. This preserves the existing `fight_known` and `tournament_known` engine paths, including their different weigh-in and weight-management context. Recovery is no longer an onboarding choice. Existing internal recovery and deload behavior remains available to the deterministic engine.

## Existing Training Model

Existing training is one scheduled session that may contain one or more components:

- Boxing
- Sparring
- Strength
- Conditioning

Supported Boxing details:

- Boxing class
- Technical work
- Pads or mitts
- Bag work
- Footwork

Supported Strength details:

- Full body
- Lower body
- Upper body
- Trunk

Supported Conditioning details:

- Steady cardio
- Intervals
- Short bursts
- Timed rounds
- Circuit

For multi-part sessions, the boxer may identify a main part or mark the session as balanced. The engine stores the session once, preserves its structured component details, and counts the component demands when building the weekly training budget. Sparring remains protected existing training and is never generated by CornerIQ.

The same behavior is available during onboarding and in Plan for recurring and one-off sessions. Plan supports direct Add, Edit, and Remove actions.

## Removed Questionnaire Data

The following former profile fields are removed from onboarding, athlete schemas, engine rules, repositories, fixtures, and generated defaults:

- Injury history
- Medical flags
- Medications
- Pregnancy status
- Eating-disorder risk questionnaire
- Prior weight-cut history questionnaire
- Medical-professional involvement

The accompanying database migration removes these rejected keys from stored profile JSON and drops `athlete_profiles.sensitive_medical`.

This does not remove current-state safety behavior. CornerIQ continues to use current readiness and symptom reports, body-mass trends, hydration signals, food logs, cycle symptoms when enabled, age, and competition context. Missing current data remains unknown rather than safe.

## Source and Title Language

- Boxer-entered schedule items use **Existing training**.
- Prescribed sessions use **CornerIQ workout**.
- Existing training titles are derived from their components, such as `Boxing + Strength`.
- CornerIQ workout titles use the canonical session-family title rather than generated or internal wording.
- Internal terms such as protected anchor, compiler, and materialized session are not used on changed athlete-facing surfaces.

## Navigation Cleanup

The visible bottom navigation contains:

- Today
- Train
- Fuel
- Plan

Profile remains a routed screen but is opened through the Account action rather than taking a daily-navigation tab. The changed screens remove repeated setup and ownership explanations while retaining safety warnings, privacy controls, and destructive-action confirmations.

## Compatibility

- Existing legacy protected-workout records remain readable.
- Legacy types map to the nearest structured existing-training component for display and planning.
- The migration changes the profile schema only; it does not rewrite completed training history.
- Wearable engine support remains dormant for future use, but onboarding and profile settings do not expose it.

## Verification

Automated handoff requires:

- `npm install`
- `npm run typecheck`
- `npm test`
- `npm run lint`
- `npm run quality`
- `npm run preflight:beta`
- Local Playwright agent audit

Human review remains required for physical iPhone keyboard behavior, safe areas, dynamic type, touch targets, and boxer comprehension of the new wording.

## Out of Scope

- Production deployment or production database migration
- Live wearable connection UI
- Generated sparring, contact drills, or unsupervised fight simulation
- Coach accounts or coach-authored plans
- New weight-cut protocols
- Final copy approval; the owner will apply the product's human voice after the interaction structure is validated
