# QA Surface Matrix

This matrix defines what evidence belongs to each beta-readiness surface. `human_review_required` is an acceptable final state when the evidence genuinely cannot be produced by local automation.

| Surface | Sub-surfaces | Automated agent QA checks | Screenshots required | Page-text snapshots required | Safety scans | Secret scans | AI qualitative questions | Human review questions | Beta-blocking conditions | Accepted limitations |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A. Code and build health | npm install, typecheck, tests, lint, quality, beta preflight, GitHub Actions quality, Expo web startup, agent QA CI | Run package gates and local QA CI; inspect workflow presence | None unless a web startup failure renders | Logs summarized in handoff, not committed | Static safety tests pass | Workflow and scripts do not require Supabase secrets | Are the gates enough to trust a controlled beta pass? | Did CI pass on the target branch? | Any required gate fails without documented blocker | GitHub Actions status may require remote review |
| B. Auth and account | Sign-in, sign-up, email confirmation, session persistence, sign-out, signed-out recovery, errors, real Supabase auth | Local E2E auth copy, sign-in, sign-out recovery smoke | Auth, signed-out recovery if added | Auth | No emergency or medical support framing | No tokens, public env values, or project URLs | Is account copy clear about beta and confirmation limits? | Real email confirmation and session persistence work? | Auth prevents all testing or exposes secrets | Real Supabase auth is human/live only |
| C. Onboarding | Boxer level definitions, body mass/height units, equipment, availability, protected anchors with RPE, cycle, wearable, safety restrictions, no medication collection, goal phase, finish setup, no internal engine terms | Full first-time path with real inputs before Today | Auth plus every onboarding step | Auth plus every onboarding step | No unsafe weight-cut, no generated contact, missing data unknown | No secrets in text | Would a boxer know what to enter? | Does a real boxer complete it without guessing? | Field likely causes wrong engine input | Human comprehension requires beta sessions |
| D. Today | First action, primary action, why disclosure, quick logs, 1-5 explanations, save feedback, missing data unknown, density, mobile | Local demo and real onboarding path, desktop and mobile Today | Today and mobile Today | Today and mobile Today | Unknown/not safe framing | No tokens in page text | Is first action obvious within 5 seconds? | Does a boxer know what to log first? | No clear first action | Phone feel needs physical review |
| E. Fuel | Command, first safe action, weight-class pressure, manual food log, hydration, missing logs, review/self-clear copy, body mass, no barcode expectation | Fuel tab, command, reviews, body mass, food log | Fuel and review/body mass evidence as needed | Fuel | Unsafe cut phrase scan, self-clear scan | No secrets | Does Fuel avoid pressure and overconfidence? | Does a boxer feel pushed to make weight? | Unsafe cut instruction or pressure | Barcode and meal planning deferred |
| F. Train | Today/Workout, generated workout, no sparring/contact, intensity, fast completion, RPE flow, exercise row, Exercise History, progression, load inference | Train tabs, workout detail open, fast completion controls, history/progression checks | Train Today, Workout detail, Workout completion, Exercise History | Train Today, Workout detail, Workout completion, Exercise History | Generated-contact scan, over-escalation scan | No secrets | Is support boxing-specific and safe? | Can a boxer complete workout logging after training? | Generated contact or unusable completion | Numeric load progression deferred |
| G. Plan | Week, Next Week, Block History, Adjustments, protect/unavailable/deload/restore, no coach controls, no drag/drop, adjustment result, roll-forward explanation | Plan tabs and adjustment controls visible, no coach/drag/drop copy | Plan Week, Next Week, Adjustments, Block History | Plan Week, Next Week, Adjustments, Block History | Coach/reviewer exposure scan | No secrets | Does Plan explain engine-owned requests? | Does next-week materialization make sense? | User cannot tell what buttons do | Drag/drop calendar deferred |
| H. Profile | Athlete, settings, data, audit, sign out, beta notice, beta health, feedback, history, export, DELETE deletion, no destructive action, no secrets | Profile Audit and Data sections, feedback, beta health, export preview, delete gate | Profile Audit, feedback, beta health, Profile Data | Profile Audit, feedback, beta health, Profile Data | No self-clear, no emergency framing | Strong secret scan | Are privacy and feedback expectations clear? | Does tester trust data controls? | Feedback unavailable or delete unsafe | Admin triage dashboard deferred |
| I. Error and recovery | Error boundary, signed-in sanitized report, signed-out retry only, no raw stacks, no emergency support framing | Static tests/docs inspect boundary sanitization and signed-out behavior | Optional recovery screen if safely triggerable | Error docs/test evidence | No medical/emergency support framing | Redaction patterns present | Is recovery copy calm and privacy-safe? | Can testers recover without support confusion? | Raw stack or secret exposure | Forced app errors can remain static-only |
| J. Engine output quality | Today, Fuel, Train, Plan outputs, beta personas, under-fueling, red readiness, weigh-in cases, cycle, manual-only, no equipment, protected sparring, prohibited support | Generate `engine-output-review.md` from deterministic personas | None required | Engine report text | Prohibited phrase, contact, self-clear scans | No secrets in report | Does output feel boxing-specific, safe, useful, and not overconfident? | Would real testers follow this safely? | Unsafe or misleading engine output | AI/human review still needed for nuance |
| K. Privacy and safety | No service role, env values, tokens, medical history, secrets in feedback, emergency details, cycle privacy, wearable optional, feedback user-owned | Static tests plus text scans | Profile Audit/Data where relevant | Profile Audit/Data | All safety blockers | All secret blockers | Is privacy copy understandable? | Do testers understand what not to submit? | Secret exposure or unsafe collection | Real privacy review may be separate |
| L. Supabase/live data | Migrations, dry run, live smoke, feedback persistence/cleanup, export/delete scope, RLS, real auth/email | Routine QA marks human/live only; no real credentials | None from routine QA | None from routine QA | Live smoke must not create unsafe state | No service-role keys | Are live blockers documented? | Release owner runs live smoke? | Migration/live smoke blocker | Explicit opt-in only |
| M. Physical mobile / iPhone | Touch, keyboard, scrolling, safe area, density, Expo Go/EAS limitation | Mobile viewport smoke only | Mobile Today plus added mobile flows when available | Mobile Today | Same safety scans | Same secret scans | Does simulated mobile reveal obvious issues? | Physical iPhone checks touch/keyboard/safe area? | Physical issues block real beta | Local E2E cannot complete this gate |
| N. Distribution/release | EAS project, preview artifact, tester list, icon/splash/metadata, private channel, build config secrets, docs, release decision | Static docs and preflight only | None from local QA | None from local QA | Release safety gates documented | Build config secret scan | Are limitations clear? | Release owner confirms artifact and tester control? | Distributed beta claimed without artifact | EAS/iPhone work remains owner-required |
