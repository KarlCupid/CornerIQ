# Known Gaps

| Priority | Domain | Issue | Why it matters | Recommended next action | Blocking |
| --- | --- | --- | --- | --- | --- |
| P1 | Progression materialization | Weekly summaries and progression decisions now persist, and `weekIndex` advances from history, but the app does not yet materialize a full next-week dose model from the decision. | A true multi-week programming system should turn `progress`, `repeat`, `deload`, `taper`, or `hold` into the next microcycle shape without inventing unsafe load math. | Use persisted decisions to shape next-week phase/volume and generated support while continuing to avoid free-text load progression. | Non-blocking for audit history, blocking for deeper automated programming. |
| P1 | Coach/team permissions | Adjustment actor checks exist, but there is no Supabase coach/team relationship model or production authorization boundary. | Future coach support needs real account relationships before coach-only actions can be exposed in UI. | Add coach/team tables, RLS policies, and trusted server/service boundaries before shipping coach workflows. | Blocking for shared coach accounts. |
| P1 | Block history detail | Plan/Profile now show compact block history, current week summary, latest decision, and timeline events, but there is no dedicated drill-down timeline. | Athletes and auditors can see the latest story, but long blocks need better review and comparison. | Add a view-model-driven block history screen that lists weekly summaries, progression decisions, and adjustment events. | Non-blocking. |
| P2 | Plan adjustment UX | Plan controls are intentionally skeletal and athlete-only in UI; coach move controls are not exposed. | The command model is safer, but repeated weekly planning still needs clearer interaction design. | Add clearer feedback, date picking, and a safer move session flow after coach permissions and roll-forward are hardened. | Non-blocking. |
| P2 | Exercise history | Analytics and weekly summaries use exercise results, but there is no exercise-history screen. | Athletes cannot inspect repeated pain flags, prescribed-only rows, or strength actuals over time. | Add a view-model-driven exercise history panel. | Non-blocking. |
| P2 | Numeric load progression | Free-text `loadText` is summarized but not parsed for progression. | Avoids fake progress and unsafe assumptions, but limits strength progression precision. | Add structured load fields later; keep free-text as notes. | Non-blocking. |
| P2 | Completion UX density | Workout detail is still dense on mobile. | The flow is functional but can feel heavy during post-workout logging. | Split completion into a lightweight sheet or stepper while preserving `prescribed_only` defaults. | Non-blocking. |
| P2 | Cycle longitudinal UX | Cycle effects are explicit in training decisions and weekly summary flags, but history remains card-level. | Symptom-aware adjustments need better longitudinal review without fertility assumptions. | Add private trend summaries driven by cycle engine outputs. | Non-blocking. |
| P3 | Calendar polish | Plan has no drag/drop or calendar package. | Weekly command center is readable but not yet a full planner. | Add after multi-week block lifecycle and permissioned adjustment commands are hardened. | Non-blocking. |
| P3 | Export format | Export/delete controls include the new progression tables, but export is still a preview/count flow. | Users will eventually need a portable artifact. | Add downloadable export bundle after data model settles. | Non-blocking. |
